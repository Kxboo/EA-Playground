# Tetherball player initialization

`src/tetherball_player_init.rs` ports the complete `MGTetherball::InitializePlayer` body at `0x8039ba00` from the pinned `playgroundz.elf` (`5cef3efc7005fb71fed0a75e60ee240ee6ac4243b00dd3296e6e53ca269a3e2c`). This module’s verified scope is that helper only.

The native `+0x210` count guard returns immediately at two or more players. Otherwise the helper queries WorldMan player zero, compares both stored identity words, and performs a third lookup only when they match. A match reuses that character; a miss invokes `SpawnCharacter` with the original identity registers, position, trailing registers, and stack words. The unused ABI alignment register is intentionally excluded from the typed spawn arguments.

After selecting the character, the function synchronously applies its CharacterState position and direction. Direction construction follows the retail `rmAngle` wrap and `AsDir` path. The helper then allocates one AI slot, conditionally constructs its AI entity, registers and binds it, and stores the existing ball handle at AI `+0x60`. It writes the selected character/AI handles into the shared `ResetState` arrays at MGTetherball `+0x120/+0x128`, and writes `+0x130[slot]` as zero for reused characters or one for newly spawned characters. Finally, it calls the multiplayer or single-player ability setup according to the byte addressed by `0x8060204c`, initializes controller state `0x12`, and increments the shared `Lifecycle.player_count` (`+0x210`) and `Lifecycle.session_mode` (`+0x40`) in native order.

`PlayerInitServices` is the synchronous boundary for WorldMan lookup, character spawn/state methods, AI pool/object/list operations, ability setup, and controller operations. It carries exact input/output handles and vectors; it does not invent successful allocation or ability results. The PPC fixture hooks these methods and executes the original function body, including the retail angle constructor, wrap, `AsDir`, and trigonometric helper. The raw game-field stores remain in the body’s typed Rust implementation.

The original-execution fixture is `_bevy/tests/data/tetherball_player_init_golden.json`, generated and checked by `_bevy/tools/tetherball_player_init_oracle.py`. Its eight cases cover counts zero and one across null, identity-match, and identity-mismatch world-character outcomes, both ability branches, signed session-word wraparound, and the two-or-more count guard. The Rust unit adapter compares ordered service calls and all modeled scalar/handle stores against those snapshots.

The shared `Lifecycle.player_count` type is unsigned, so the port targets the valid game domain of nonnegative participant counts. The native instruction uses a signed compare; negative or corrupt raw counts are outside this typed domain. InitializeAI and InitializeAdditionalPlayer are not claimed by this module.
